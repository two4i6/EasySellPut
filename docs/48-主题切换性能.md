# 主题切换性能

## 问题与改动

macOS 的旧实现每次切换明暗都创建语义画刷，然后先移除旧资源字典再添加新字典。原生主题重解析之外还产生两次自定义资源失效。现在预先构建两种明暗 × 两种涨跌约定的不可变配色，交给 Avalonia ThemeDictionaries 解析；明暗切换不再安装/卸载自定义字典。涨跌约定切换使用一次缓存字典替换；相同有效配色不重复通知消费者。

Windows 的旧实现每次逐项写全局资源，并让 WPF-UI 更新系统强调色。WPF-UI 4.3.0 的强调色更新本身还会写入几十项根资源。现在应用自己的完整冻结配色通过一个字典安装/替换，复用已创建的画刷；显式明暗、系统跟随及系统 watcher 都不再重复应用 OS accent。应用仍按现有 tokens 使用 Claude 风格语义色，保留系统主题跟随、纯色窗口、窗口 watcher 的卸载和涨跌约定。

没有改变主题持久化协议、页面/网页会话生命周期、业务逻辑、行情刷新频率或 CLI/MCP 操作。也没有为提升数字关闭按钮交互动画或减少动效支持。

上游实现核对：[ApplicationThemeManager](https://github.com/lepoco/wpfui/blob/4.3.0/src/Wpf.Ui/Appearance/ApplicationThemeManager.cs)、[ApplicationAccentColorManager](https://github.com/lepoco/wpfui/blob/4.3.0/src/Wpf.Ui/Appearance/ApplicationAccentColorManager.cs)。使用与项目依赖相同的 4.3.0 标签。

## 测量

Linux 云环境中的真实 Avalonia/Skia headless 控件，1920×1080：先访问全部页面并回到设置页，预热后连续切换 12 次。相同测试分别在改动前后独立进程执行：

| 指标，中位数 | 优化前 | 优化后 |
| --- | ---: | ---: |
| Theme.Apply 同步处理 | 27.17 ms | 16.50 ms |
| 应用 + 5 次强制渲染/排队工作处理 | 197.36 ms | 191.49 ms |

同步阶段约减少 39%。第二行不是单帧时长，也不是用户在 macOS 真机上的点击到显示延迟，包含测试框架强制的 5 次渲染。完整测试进程内再次运行得到同步阶段约 8 ms，说明预热与主机负载会影响绝对值；不把该数值与独立进程基线作为严格对照。原始数据：[before](theme-performance/before.json)、[after](theme-performance/after.json)。Windows 没有本地原生性能数值。

## 验收与 CI

- 两端新增配色复用、重复应用不通知、不增长应用资源字典的回归测试。
- macOS 连续切换保留页面实例，不增加报价/K 线请求；全部页面可见和隐藏时的运行期切换，与对应初始主题的像素及语义资源对照继续通过。
- `bash build/test-headless.sh`：806 项离线 .NET 测试通过（Core 198、Data 135、Analytics 206、Shared 86、Mac 111、Automation 70）；54 项 Python 门禁及 47 项真实 CLI/MCP 对照通过。
- Windows 应用和完整 WPF 测试项目交叉构建通过；现有 WindowChromeTests 可空性警告未由本次引入。Windows 原生执行仍需 GitHub Actions，不能把交叉构建当作 WPF 运行验收。
- 既有 CI 运行完整 Mac/WPF 测试；本次额外将 `MEILI_THEME_PROFILE` 指向 UI artifact 目录，上传测量 JSON。没有使用容易受 CI 负载影响的毫秒硬阈值，缓存复用、重复通知和数据请求数量为确定性门禁。
